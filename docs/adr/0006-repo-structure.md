# Repo structure: three component buckets, a grouped assistant, and a site route group

`components/` was half-organised — some feature folders, some loose files at the root — and `lib/` listed four concerns at one level even though three of them were all "the assistant." Issues #100–#108 restructured the tree with zero behaviour change and no public-URL change. The shape it landed on, and why:

**`components/` has exactly three buckets.** `ui/` is generic and presentational with no domain knowledge (custom cursor, cover-image wrapper); `layout/` is site chrome (navigation, footer); `features/` is one folder per domain concept or page section (`home/`, `project/`, `chat/`, `theme/`). The rule has no exceptions — nothing sits loose at the root — so "where does this component go" is answerable from the three definitions alone, and the full surface of a feature change is one folder. The cover-image wrapper counts as `ui/` despite taking a Sanity image, because its only coupling is the URL builder.

**`lib/assistant/` groups the chatbot's three concerns.** `chat/`, `corpus/`, and `guardrails/` moved wholesale under `lib/assistant/` so the boundary of "the assistant" is one directory. `lib/sanity/` stays a top-level sibling to keep the data layer's independence obvious, and the rule that only `lib/sanity` constructs the Sanity client is preserved through the move. `lib/theme/` is the third member: a constants module so the theme storage key, dark-class name, and media query are defined once and shared by both the pre-hydration `<script>` and the hook.

**`app/(site)` is a route group, not a URL segment.** The root `app/layout.tsx` keeps only the document shell, fonts, the theme bootstrap `<script>`, and `ThemeProvider`. The `(site)` layout owns the site chrome — custom cursor, chat shell, navigation — so `app/studio` (outside the group) renders none of it. Route groups do not affect paths, so `/`, `/projects/<slug>`, and `/studio` are unchanged.

**Testing philosophy: assert behaviour, not markup.** A test should fail only when externally observable behaviour regresses — what a visitor sees, or what a caller receives. Assertions that only check a class name is present, or that the DOM nests a particular way with no behavioural consequence, were deleted or rewritten in the #107 pass. The `lib/` unit tests and API-route tests (chat context building, the `/api/chat` route, retrieval, guardrail units) are the model: they assert on returned values and observable effects.
